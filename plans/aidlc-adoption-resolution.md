## 2. Решения по спорным и новым пунктам

### 2.1 Обход через отсутствие `Consumes` ([B] P1-1). Принято, закрыто по умолчанию

[B] прав: если `Consumes` необязателен, планировщик обходит проверку, просто не объявив его. Обязательная разметка
каждой зависимости — лишняя нагрузка на планировщика. Поэтому решение такое: **выводить по умолчанию, отказываться
явно.**

- **Новый режим.** Он действует при `StepOutputs` + `TypedCriteria`. Прямая зависимость от шага, у которого есть
  поле-список (`path[]`/`string[]`), **считается** consume всех его списков.
- **Отказ от consume.** Шаг может явно сказать, что зависимость нужна только для порядка: `"after": [0]` вместо
  `"dependsOn"`, по аналогии с `requires_stage` и `consumes` в AI-DLC. Ещё один вариант — `"subset"`, см. §2.3.
- **Ошибка плана.** Список, который потребляется, а у потребителя нет поля, куда положить покрытие, ломает план. Это
  ошибка, и с диагнозом идёт replan, как сказано в [A] (новый вызов `ReplanAsync` по образцу `Orchestrator.cs:541-605`).
  Тихого `ErrorObserved` больше нет.
- **Обязательный тест:** план `pages: path[] → text` **без** всяких объявлений отклоняется. Этот тест проверяет
  главный заявленный результат фазы.
- **Передача полей.** §1.4 (передавать только потреблённые поля) применяется только к явным `Consumes`. Выведенные
  consume передают всё, как сегодня.

### 2.2 Чем доказывается элемент ([B] P1-2). Принято, вид доказательства объявляется

Подтверждено по `EvidenceCoverage.cs:83-85`: `call` засчитывается по **любому** успешному вызову, в аргументах
которого есть элемент. Это доказывает обращение к элементу, но не действие над ним. Выводить вид доказательства из
типа списка (`path[]` → `file_read`) нельзя: «создать», «удалить», «проверить» требуют разного.

Решение:

- **Где объявлять.** Вид доказательства пишется в объявлении consume: `"evidence": "read" | "write" | "command" | "mention"`.
  Для выведенного consume по умолчанию берётся `mention`, то есть сегодняшний `call`. Это самый слабый вид, и он
  честно называется «упомянут».
- **Новый вид `write`.** Элемент засчитан, если шаг его записал, удалил или переименовал. Сведения берутся из
  `ChangeAuthorship` и журнала.
- **Что проверяет движок.** Только *наличие* результата и доказательства для каждого элемента. *Достаточность*
  действия по-прежнему оценивает ревьюер. В уровне `mention` это прямо написано, поэтому правило не превращается в
  «аудит файлов» в универсальном движке.

### 2.3 `subset` ([B] P1-3). Принято, разделение полей и проверка ревьюером

- **Две части результата.** Вместо одного `results` с причинами внутри вводятся `processed` (элемент → результат) и
  `excluded` (элемент → причина). Движок проверяет детерминированно две вещи:
  - `processed ∩ excluded = ∅`;
  - `processed ∪ excluded = source`.
  
  Пропущенных элементов не остаётся ни в каком режиме.
- **Законность исключений** флаг не доказывает. Список `excluded` с причинами всегда уходит ревьюеру как отдельный
  блок с вопросом «разрешал ли запрос это исключение». Без ревьюера (`ReviewOn=false`) исход шага с непустым
  `excluded` максимум `DoneUnverified`, но не `Succeeded`.

### 2.4 Гейт при выключенном ревью ([B] P1-4, [A]). Свой бюджет

- **Порядок.** Гейт выполняется **до** ветки `ReviewOn` (`Orchestrator.Attempt.cs:31`) и не зависит от неё.
- **Бюджет.** Retry считается отдельно: `GateRetries`. По умолчанию он равен `ReviewRetries`, а при выключенном
  ревью равен 1. Объяснение для кода: без ревьюера сегодня всего одна попытка, и при провале покрытия шагу нужен хотя
  бы один шанс дописать работу.
- **Дешёвая подсказка.** Сначала используются существующие ранние точки из [A]:
  - `CallAdmission.cs:733-736` при submit сообщает «не покрыто X»;
  - `StepEnding.cs:190-208` срабатывает в конце шага.
  
  Полный retry остаётся последней мерой.
- **События.** Гейт сам публикует `ReviewFailed` с источником `engine` (прецедент — `OutOfBudget`,
  `Orchestrator.Review.cs:65`).

### 2.5 Join ([B] P1-4, [A]). Контракт частичного результата

Join **никогда** не становится `ReviewRejected`, потому что частичный результат ценен.

- **Исход join.** Остаётся как сейчас: `DoneUnverified` + `ItemsUnfinished`, результаты завершённых элементов
  сохраняются.
- **Список непокрытых элементов** записывается как blocking-критерий **прогона**. Прогон не может стать зелёным, но
  зависимые шаги выполняются.
- **Шаг-отчёт после join** получает явный список «не покрыто: …» в hand-off и обязан его упомянуть. Это проверяется
  тем же механизмом consume с видом `mention`.

### 2.6 Проверяемое состояние файлов (фаза 3, [B] P1-5, [A]). Узкий v1

| Вопрос | Решение v1 |
| --- | --- |
| Откуда changed paths | Журнал файловых инструментов (`ToolResultAccounting.Record`) ∪ diff снимка, если он есть. Так ловятся и изменения через shell. Только журнала недостаточно |
| Staging | Blocking step-чеки в staged-режиме **не выполняются на шаге**, а переносятся на границу apply/run. Пока staging не умеет отдавать материализованное представление, команда, читающая диск, проверяла бы старый файл |
| Параллельность | Blocking step-чеки только при `MaxParallelSteps == 1`. Иначе чек выполняется на границе волны (`ValidateWaves`), где состояние стабильно |
| Write-чеки | Только advisory, как в AI-DLC. Работают в любом режиме, потому что ничего не решают |
| Разрешения | Если политика не разрешает команду без вопроса, blocking-чек получает `Unknown`, а шаг — `DoneUnverified`. Об этом прямо говорится в UI, а не происходит молча |
| Анти-тампер | До заявления «воркер не правит свои чеки» нужен тест, что **shell** не пишет в `.enactive/checks/`. Сейчас такой проверки не найдено |

### 2.7 `StepCommit` (фаза 4.1, [B] P1-6, [A]). Отложить до модели владения

Ревью сходятся с двух сторон. [A] показал, что коммит размазан шире, чем в плане (`JoinAsync`, `ExpandAsync`,
чекпоинты в L2030/2166/2197), и что на пути отказа есть гонка `MarkFailed`/`StepCompleted`. [B] показал, что
`Apply → effects` без единого владельца теряет обновления и не атомарен.

Решение:

- **Сейчас.** Сделать только 4.0 (характеризация) и **отдельный фикс гонки** `MarkFailed` до `StepCompleted`.
  Гонку не закреплять тестом как правильное поведение.
- **4.1 начинать только после дизайна,** в котором определены три вещи:
  - единственный владелец `RunState`: один цикл или канал, `Apply` выполняется строго последовательно;
  - момент фиксации: чекпоинт — это точка коммита, события публикуются после неё;
  - поведение при сбое каждого effect.
  
  Обязательны тесты с отказом записи чекпоинта и перезапуском, а не только с порядком событий.
- **Полнота по enum.** Утверждение «switch без default — это ошибка компиляции» неверно: `TreatWarningsAsErrors=false`
  (`Directory.Build.props:8`). Нужно использовать switch-*выражение* и поднять `CS8509`/`CS8524` до ошибки через
  `WarningsAsErrors` в проекте Agents. Плюс тест, который проходит `Enum.GetValues<StepOutcomeKind>()`.
- **4.2 (пауза) от 4.1 не зависит.** Её можно делать через существующий `hold` в `StepDispatcher` и назвать `Paused`
  (имя `Parked` занято). 4.3 не делаем.

### 2.8 Resume и версии ([B] P2-8, [A]). Сохранять содержимое, а не хеш

- **Чекпоинт.** В `CheckpointStep` и `PlanOf` попадают `Consumes`, выведенные критерии с их видом доказательства и
  `GateRetries`.
- **Чеки.** Снимок манифестов хранится в чекпоинте целиком. При resume используется **снимок**. Если манифест на
  диске изменился, это видно в UI: «прогон продолжен со старыми чеками; изменённые: X». Выбор «перечитать» есть только
  у старта нового прогона.
- **Правила (фаза 5).** В записи прогона хранится **полный текст** применённого набора правил: он короткий, размер
  ограничен cap. Хеш в `RunSettings` служит только ключом для сравнения.
- **Тест:** сохранить → изменить чеки и правила → возобновить. Прогон работает по сохранённому.

### 2.9 Цикл обязательств (фаза 2, [B] P2-7, [A]). Сохранять отказ структурно и ограничить общий счёт

- **Отказ структурно.** Подтверждено: отклонённая подача не сохраняется («Nothing was stored»,
  `CallAdmission.cs:747`), а `OutputSlot.LastRefused` — это строка. Состояние «4 из 6» сейчас недоступно. Нужно
  добавить в слот структурную диагностику последнего отказа (`MissingFields`, `InvalidFields`) отдельно от принятого
  результата. Тогда сигнатура строится из неё.
- **Циклы A → B → A.** Помимо счётчика «без изменений» вводятся:
  - множество уже виденных сигнатур: повтор не считается прогрессом;
  - общий потолок nudges на шаг, жёсткий, с комментарием «почему».
- **Дефолты.** «1/1 = сегодня» неверно, [A] это тоже пропустил и уже исправил. Совместимый дефолт: лимит на **каждый
  вид** обязательства = 1, общий потолок = число видов. Только так поведение до замера bench остаётся прежним.
- **Первым PR** (из [A]) идёт исправление ситуации, когда шаг, у которого критерий всё ещё не выполнен, заканчивается
  `Succeeded` без события (`StepEndingTests.cs:129-141` закрепляет это поведение). Это нужно до любой переделки
  цикла.

## 3. Что из [A] остаётся в силе и в [B] не упомянуто

- Неверные точки врезки в плане:
  - `CallAdmission:792` → `ToolResultAccounting.Record`;
  - `EvidenceBudget` как guard контекста → `Turn.ContextWindow` и существующий «window full»;
  - `CanApprove` ≠ «attended».
- Фаза 5:
  - `DefaultWorkers.Augment` вызывается раз на хост и входит в кешируемый префикс, поэтому правила нужны отдельным
    per-run блоком;
  - Global-слою нужен машинный стор, в SQLite/JSON его нет;
  - поле `lessons` у ревьюера отложить: промпт подстроен под замеры, лимит вывода 2048 токенов.
- Фаза 3:
  - есть только `DotnetEcosystem`, ограничение неявных `build`/`test` надо назвать;
  - blocking-регрессия отменяет явное решение run 3fe4f8, поэтому только opt-in.
- §3.4 (исчезнувшие тесты в `CompareTests`) — независимое изменение, его стоит делать рано.
- Факты об AI-DLC: `upstream-coverage` у них advisory, есть ещё `cites:`; `report` не единственный мутатор;
  carve-outs в Stop hook.

```

PR 0b  гонка MarkFailed → StepCompleted на пути отказа (+ тест)
Ф1a    consume выводится по умолчанию + "after" для порядка + replan при ошибке + персистентность в чекпоинте
Ф1b    гейт до ReviewOn, GateRetries, evidence-виды (mention/read/write/command), processed/excluded
Ф1c    join: частичный результат + blocking-критерий прогона; отчёт обязан назвать непокрытое
Ф3.4   исчезнувшие тесты в CompareTests (+ Protects)
Ф2     структурный отказ в OutputSlot → ObligationLoop (лимит на вид + общий потолок + цикл-детект)
```

## 5. Что решает владелец

1. **Закрытость по умолчанию (§2.1).** Согласны ли вы, что в новом режиме любая зависимость от списка — это
   consume, пока не написано `after`? Это изменит поведение существующих шаблонов при включении флагов.
2. **Слабый вид доказательства (§2.2).** Достаточен ли по умолчанию `mention`, или по умолчанию требовать `read` для

3. **Staging (§2.6).** Устраивает ли перенос blocking-чеков на apply, или нужна материализация staged-представления
